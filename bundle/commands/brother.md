# Brother

One door. Read `$ARGUMENTS` for what the work IS, never for a product name the person is not expected to know. `brother-run` below is the launcher this plugin ships: `"${CLAUDE_PLUGIN_ROOT}/runtime/brother-run"` under Claude Code, `"${PLUGIN_ROOT}/runtime/brother-run"` under Cursor, `"${BROTHER_PLUGIN_ROOT}/runtime/brother-run"` as the vendor neutral name. In a checkout of the Brother repository, where no plugin root is set, run `python3 scripts/brother_run.py` with the same arguments.

## Bare `/brother`, or "continue"/"resume"

Follow the single authoritative decision order in `skills/using-brother/SKILL.md`. The two steps below are this command's mechanics for that order's rows 1 and 2, never a second rule.

**Step 1, check for unfinished work before asking anything:**
`brother-run --continue --cwd <this repository>`. None: it prints "no
unfinished run found" at exit 0, so fall through to Step 2. One: it resumes
and prints a sentence naming the OUTCOME; relay that, never the run
directory. Several: relay its numbered outcomes, re-run with `--continue N`.

**Step 2, no unfinished work: ask the one question.** Say exactly this and
nothing else: "Brother turns AI-assisted work into something checkable
instead of just trusted. What are you trying to do?"

That is the most a normal task is asked: one genuinely blocking question.
Never make the person choose an internal product name, an autonomy code, a
plan format, a run id or a test framework before starting. "Continue the
unfinished task" is Step 1 and nothing else: the engine's own run discovery,
never a second run database.

## BUILD IT: you write the plan, the engine runs it

When the ask is a thing to BUILD, add, fix or change in the repository this session sits in, and Step 1 found nothing: first write the outcome contract (the intake, `bm_project.py adopt`, reference skills/using-brother/references/intake.md): the language the answer owes, the question asked, the checks that prove it done. Then decompose the outcome YOURSELF into 2 to 9 units (`id`, `objective`, `done_check`, `writes`, `deps`), write them as a JSON list to a file outside the repository, and run `brother-run "<the outcome>" --cwd <this repo> --contract <the record> --plan <that file>`; some unit must run each check the contract promises. It opens one isolated worktree per unit, three at most. Inside a session it spawns no worker: it exits 3 naming each unit's worktree, check and writes, and those units are YOURS. Do each in its worktree, leave the work there, then run the `--continue` line it prints: that commits each lane, re-verifies every check and integrates what passes. Exit 0 means all integrated; nonzero names each refused unit and why. Without either flag it refuses at NO-DATA in a session. Unit rules: `using-brother/references/router-details.md`.

## Routing by intent

**Incident first.** An ask saying something is broken now (down, outage,
hotfix, 落ちた) routes to `start` with the incident named verbatim, in
assurance mode, never a status, board, forecast or handover path.

Six verbs, one row each, generated from the installed skills by
`scripts/gen_door_table.py`, never typed by hand:

Pick the row from the words used. The mode a verb runs in is read from the
work, never asked: assurance when the ask describes a change someone must
trust (a schema or migration, an API contract, money, personal data, a
production path, a diff to review, a number about to be claimed true),
execution provenance for a project, outcome, plan or status question. "Show
me what happened" is `status`: it reads the run's receipt. "Verify this
change" is `review`: the gates run inside it. An ask matching no row above
never silently becomes `start`: name the closest row in one sentence, in the
language they wrote in, and ask the one thing that would settle it.

## The 1.1.0 names still route

An argument opening with a 1.1.0 skill name (`brotherme-`, `brothermode-` or
`brothersbe-` followed by its verb) is looked up in
`${CLAUDE_PLUGIN_ROOT}/skills/using-brother/references/retired-names.md`: say
one line, `<old name> is now /brother <verb>`, then route as that verb with
the words the table gives it and the rest of the request.
A name with one of those prefixes that the table does not list is unknown:
say so and ask Step 2's question, never guess a verb. On a host without slash
commands the pointer names the verb skill (`brother-<verb>`), never a slash
command that host cannot run. Typed as it was, `/brother:<old name>` is a
moved command that says the same line and routes the same way.

## handover, board and cut

**handover** ("wrap up", "close the session") runs `scripts/handover_ceremony.py`;
**board** ("the gantt", "what slipped") runs `scripts/gen_readiness_board.py` and
`scripts/track_delivery.py`; **cut** ("cut 1.0.19", "ship the release", "is the
release ready") runs `scripts/cut.py` for the person, who never types a command.
All are this repository's own: inside it, read and follow
`docs/maintainer/BROTHER-MAINTAINER-VERBS.md`; elsewhere, say so plainly.

## loop health: never make the person guess

**loop** ("is the loop working", "why did the loop stop", "loop status", "is
repair.loop running") runs the watch and relays its answer, never a reading of
the log by eye: `python3 scripts/loop/loop_watch.py --explain` from a checkout,
or `python3 "${CLAUDE_PLUGIN_ROOT:-$BROTHER_PLUGIN_ROOT}/runtime/loop/loop_watch.py" --explain`
from an install. It prints the verdict (HEALTHY, ACT with its class, or NO-DATA),
and when the loop stopped or refuses, a CAUSE line naming the exception and the
innermost frame, or the refusal, budget or hold that caused it, then a FIX line
with what to do about it. Relay all three lines in plain words, then act on the
FIX yourself when it is yours to do (a source fix with its failing test, a
cleared refusal, a relaunch); only a budget raise or another owner decision goes
to the person, as one question. While a loop runs, poll this verdict in the
background and speak up the moment it leaves HEALTHY, before anyone asks.

## What this never does

- Never a menu of skills or commands, at zero arguments or any other.
- Never "unknown command": a Brother-shaped ask maps to a cell above, and a
  genuinely unclear one gets Step 2's single question.
- Never claims an uninstalled capability: the six skills above are the whole
  installed surface, and claim verification is not in this release.
- Never makes the person choose a product name, an autonomy code, a plan
  format, a run id or a test framework.
- Holds no state and makes no PASS, FAIL or NO-DATA verdict of its own.
- Hands the person exactly one command and never writes the answer for him.
