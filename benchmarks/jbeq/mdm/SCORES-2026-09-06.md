# JBEQ-MDM scores under scorer 2026-09-06.2

Founder ruling 2026-09-06 (question UI, about 17:57 JST), verbatim: "One class
for scoring; engine keeps the proposal gate." Decision record:
`docs/decisions/decision-p0-3-reject-vs-keep-2026-09-06.json` and `.html`.
Background: `~/.claude/evidence/review-u1-2026-09-06.md` section A and
`benchmarks/jbeq/mdm/runs/blind-round9-2026-09-06/RECORD.txt`.

`scripts/jbeq_mdm.py`'s `SCORER_VERSION` is now `"2026-09-06.2"`
(`"2026-09-06.1"` was the engine-half derivation of this same boundary, hub PR
408's proposal gate). Wherever a case's own `expected` answer is REJECT MATCH
or KEEP SEPARATE, the scorer now accepts either as correct for that case (one
equivalence class for a refuted identity); the per-case line in the score
output still names which of the two the engine actually said. The
false-merge and conservative-wrong classifications are unchanged, because
neither REJECT MATCH nor KEEP SEPARATE is ever a merge answer.

Records keep their original score.txt; score-v2.txt is the same answers under
the ruling's scorer.

## A bug this same change caught before it landed

While building this table, `cmd_score`'s engine-decided/direct-answered split
(the decisions.jsonl branch, review-u1-2026-09-06.md finding 1) still compared
`answers.get(case_id) == case["expected"]` (a bare equality) instead of the
new `answers_equivalent()` used everywhere else. `passed` (used for
`direct_passed = passed - engine_passed`) counted an engine-decided
equivalence hit as correct; `engine_passed` did not; the difference leaked
into `direct-answered` as a phantom case not on any track (observed on
blind-round4-2026-09-05: `direct-answered ... 28 of 25`, more answers than
that run has direct-answered cases). Fixed in the same commit as the scorer
change; regression test
`test_an_engine_decided_equivalence_hit_counts_toward_engine_decided` in
`scripts/test_jbeq_mdm.py` pins it. Every score-v2.txt below was generated
after the fix.

## An unrelated, pre-existing confound disclosed rather than hidden

HI-01's frozen-seed label was corrected from KEEP SEPARATE to LINK AS RELATED
by an earlier, already-merged commit (`90e466dc7`, founder ruling on rule D,
`docs/decisions/decision-p0-3-rule-d-hi01-2026-09-06.json`), unrelated to this
task's ruling. Re-scoring an old run's answers.json against TODAY's frozen
seed necessarily uses that corrected label, so any run whose engine answered
KEEP SEPARATE for HI-01 (matching the *old* label) now shows HI-01 as a new
critical wrong that has nothing to do with SCORER_VERSION. This affects
blind-round4-2026-09-05, blind-round5-2026-09-06, blind-round6-2026-09-06,
blind-round7-2026-09-06, regression-2026-09-06-decide-a and
regression-2026-09-06-round5-repair (their engine's HI-01 answer was KEEP
SEPARATE); blind-round3-2026-09-05 already answered HI-01 wrong under either
label (ESCALATE) so its critical-wrong count is unaffected; blind-round8-2026-09-06
and blind-round9-2026-09-06 already answered LINK AS RELATED, matching the
corrected label, so they are unaffected too. The four U1-based runs score
against `unseen-2026-09-06.json`, which HI-01 never touched, so they carry no
part of this confound. It is called out per row below so nobody reads a
critical-wrong delta as evidence about the REJECT MATCH/KEEP SEPARATE ruling
when it is really about rule D.
