## UNSUPPORTED_TRACKS finding (read at decide time, before any answer)

scripts/jbeq_decide.py's UNSUPPORTED_TRACKS = {"survivorship", "requirements"}
(exact string match). The second unseen set's own prompt files carry
TRACK: requirements-understanding (verbatim, all five of V-36..V-40), not
TRACK: requirements as U1's corpus did. Because the check is an exact
string match, "requirements-understanding" does NOT fall into
UNSUPPORTED_TRACKS: the engine ran its ordinary rule table against V-36
through V-40 instead of returning the track-unsupported NO-DATA it gives
every survivorship case. This is a genuine corpus/engine naming drift, not
an extractor error (TRACK is copied verbatim from each prompt file per the
extractor prompt's own instruction). Per the run's own charter ("direct
answers for the tracks the engine does not decide, read UNSUPPORTED_TRACKS
now"), only survivorship (V-16 through V-20, all five of which the engine
returned as NO-DATA/track-unsupported) received direct answers from me;
requirements-understanding was left as engine-decided, since by the
current, actually-read value of UNSUPPORTED_TRACKS it is not an
unsupported track. This means requirements-understanding's 3 of 5 score
below is a real property of the engine's general rule table being applied
to a track it was not written for, not a gap I chose to paper over with a
direct answer.

## Critical wrong cases, with the engine's own rule_fired (from decisions.jsonl)

V-02  answered REJECT MATCH, expected KEEP SEPARATE
      rule_fired: rule_r
      why: stated_relation=none and object_type_a='site' !=
      object_type_b='sold_to': two different kinds of record are never
      the same operational object.
      Trace: my fact sheet set object_type_a="site" (the delivery/
      aggregation base) and object_type_b="sold_to" (the customer store),
      which is what triggered rule_r's REJECT MATCH rather than the
      seed's KEEP SEPARATE (a same-address-only, no-stated-relation
      case). A same-address case with distinguishable object kinds and no
      other refuting fact reads, on this evidence, as KEEP SEPARATE to
      the seed rather than REJECT MATCH; rule_r is stricter about
      differing object kinds than the seed's own answer for this shape.

V-03  answered KEEP SEPARATE, expected SUGGEST MERGE
      rule_fired: rule_r
      why: stated_relation=none and lifecycle='relocated': a closed,
      relocated or reused-identifier record is never folded into a live
      one.
      Trace: my fact sheet set lifecycle="relocated" for the pre/post
      move store records (same store code, moved within the same city,
      billing and payment history already booked). rule_r treats any
      "relocated" lifecycle as a hard stop against merging. The seed
      reads a same-store-code relocation with existing history as strong
      identity evidence for a person-confirmed SUGGEST MERGE rather than
      a lifecycle bar to any merge at all.

V-22  answered KEEP SEPARATE, expected REJECT MATCH
      rule_fired: rule 1
      why: stated_relation=none: the input states no relation.
      Trace: this is a requirements-understanding case run through the
      general rule table (see the UNSUPPORTED_TRACKS finding above); the
      case is actually a retroactive-reassignment request that the
      input's own migration policy explicitly forbids (transactions
      before the effective date are to stay with the old office). My
      sheet did not carry a field the general rule table reads as a
      policy-violation refutation, so it fell through to rule 1's
      default (no stated relation) instead of a REJECT MATCH.

V-36  answered REJECT MATCH, expected KEEP SEPARATE
      rule_fired: rule_r
      why: stated_relation=none and authoritative_identifier=conflicting:
      the identifiers that should govern this decision disagree outright.
      Trace: my fact sheet set authoritative_identifier="conflicting" for
      two side-by-side loyalty-member records with two different, plainly
      distinct member numbers and nothing connecting them. rule_r reads
      two disagreeing identifiers as a refutation (REJECT MATCH); the
      seed reads two merely-different, never-linked member numbers as
      KEEP SEPARATE (nothing to reject, nothing to record). In hindsight
      "absent" (no shared identifier exists at all between two unrelated
      records) fits this case better than "conflicting" (which I have
      otherwise reserved for two identifiers stated as directly disputing
      the SAME claim, e.g. two valid corporate numbers for what a
      dedup engine proposed as one entity).

V-37  answered KEEP SEPARATE, expected ESCALATE
      rule_fired: rule 1
      why: stated_relation=none: the input states no relation.
      Trace: another requirements-understanding case on the general rule
      table. The case states the requirements doc has NO decision rule
      for disagreeing currency codes, and the two billing records'
      currency codes disagree. My sheet recorded the disagreement in
      contradicted_attributes but carried no evidence_reasons entry the
      general rule table reads as escalation-worthy, so it fell through
      to rule 1's no-stated-relation default (KEEP SEPARATE) instead of
      the seed's ESCALATE (facts exist, no rule closes it).
