THE FINDING THIS ROUND SURFACES. Of the seven frozen REJECT MATCH cases, only
the three phrased with an explicit "〜を根拠に照合/統合してよいか" clause
(AD-10, MM-02, MM-03) extract to requested_action=match_on_stated_basis and
resolve correctly through the engine's gated_reject path. The other four
(AD-03, AD-04, EO-04, ID-05) ask a bare identity or open question with no
named evidentiary basis; EXTRACTOR-PROMPT.md's own rule ("Set
match_on_stated_basis when the question itself PROPOSES a match... AND NAMES
the basis it rests on") and the task's own framing ("an open question...
records none") both point a literal, blind reading toward
requested_action=none for these four, which never reaches gated_reject and
falls through to KEEP SEPARATE instead of the expected REJECT MATCH. This
reproduces, for a different reason, the same three misses (AD-03, AD-04,
EO-04) that fixture b's own default-fixture regression run shows regressed
against fixture b's pre-proposal_gate baseline this same session (see
`python3 scripts/jbeq_regression.py` output, 3 regressions), plus ID-05 as a
fourth case in the same family this round's extraction did not flip. Whether
the fix belongs in the PROMPT (treat a bare identity/open question over a
case that also carries a stated-difference or reused/cross-domain identifier
fact as match_on_stated_basis too) or in the ENGINE (let gated_reject fire on
authoritative_identifier=conflicting alone, without requiring
requested_action=match_on_stated_basis) is a decision for the rule lane, not
this extraction; this run reports the four misses and their common shape
rather than re-guessing an extraction value to force a different score.
