EVERY CRITICAL WRONG, with rule_fired (only one; the scorer names no other):

  TM-01 expected R1, answered NO-DATA. rule_fired=rule_r. why: "rule rule_r
  chose 'KEEP SEPARATE', which is outside this case's own allowed_answers
  ['R1', 'R2', 'NO-DATA']; remapped along CAUTION_RANK to the nearest
  allowed answer instead of NO-DATA: stated_relation=none and
  lifecycle='closed': a closed, relocated or reused-identifier record is
  never folded into a live one".

  Root cause, stated plainly: the fact sheet set lifecycle="closed" for
  TM-01 because R1 (港南店) is stated as eventually closed (valid_to
  2024-03-31), which is a true fact about the record overall. But the
  question's as_of date is 2024-02, which is BEFORE that closure. rule_r
  gates on lifecycle=='closed' as a flat boolean and never consults
  effective_dates.as_of against effective_dates.prior_valid_to (which the
  fact sheet DID carry, correctly, as "2024-03-31") to see the closure
  postdates the asked-about date. Compare TM-09, which hits the exact same
  rule_r path (also lifecycle='closed') and is NOT flagged wrong: there,
  the as_of date (2026-03-15) genuinely falls in the gap after R1's own
  closure and before R2 reopens, so NO-DATA is the right answer for that
  one. The same lifecycle value and the same rule produce a right answer
  in one case and a wrong one in the sibling case, because the gate does
  not look at the dates it has available. This is a rule_r ordering/scope
  gap worth a follow-up fix (consult prior_valid_to vs as_of before
  applying the lifecycle gate, or run the temporal_before_successor /
  temporal_at_or_after_successor rules ahead of rule_r on the temporal
  track), not solely an extraction defect: the fact sheet's own dates were
  correct and sufficient to distinguish the two cases; the engine did not
  use them.
