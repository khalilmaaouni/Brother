## 1. What Jev is and is not

- Jev is TypeSafe's flagship model and the first "System One" model. [DOC] https://docs.typesafe.ai/introduction
- System One models are built to make fast, structured decisions that software can use directly: they evaluate a state and typed questions and return typed answers and probability distributions, not generated text. [DOC] https://docs.typesafe.ai/concepts/system-one
- Jev does not write replies, produce code, or generate explanations of its reasoning; you define the possible answers through the three primitives. [DOC] https://docs.typesafe.ai/concepts/system-one
- Jev is not an agent: it does not generate code or choose its own next action. System One is meant to sit inside software that keeps control flow, deterministic rules, and side effects in code. [DOC] https://docs.typesafe.ai/concepts/how-to-build-with-system-one
- Input type: Jev currently accepts text input only, as a string, JSON object, or array of text values. Images, audio, and video are not supported (yet). [DOC] https://docs.typesafe.ai/concepts/system-one and https://docs.typesafe.ai/concepts/state
- Language: English is the primary training language and where accuracy is currently best. Other languages, including CJK scripts, are accepted but currently have lower accuracy; TypeSafe recommends testing on your own content and paying close attention to confidence when routing non-English workloads. [DOC] https://docs.typesafe.ai/models and https://docs.typesafe.ai/concepts/state
- Customization: Jev is not fine-tuned or LoRA-adapted with customer data; the same weights serve every account. You shape its answers per use case through the request (state content, question instructions/criteria) rather than per-account model weights. [DOC] https://docs.typesafe.ai/models
- Limits stated on the Models page for jev-1.13.0: context length is 64k tokens per request, covering the state plus all questions combined; a 32k-token sub-budget applies to the state plus the single longest question. [DOC] https://docs.typesafe.ai/models
- Elsewhere, the number of questions per request is described as "limited only by the request's token budget, which the state and the questions share. The budget is around 32,000 tokens, roughly 150,000 characters of English text." [DOC] https://docs.typesafe.ai/primitives
- Rate limits for jev-1.13: 250,000 tokens per second and 1,200 requests per minute; TypeSafe states these limits "are adjusting dynamically" and "can change without notice," with higher limits available on custom/enterprise plans. [DOC] https://docs.typesafe.ai/models
- Speed: "Most queries complete in about 100 ms. System One is fast enough for real-time request paths and user interfaces." [DOC] https://docs.typesafe.ai/concepts/how-to-build-with-system-one
- Separately, the use-case map describes System One as offering "frontier intelligence at real-time speeds (150ms)," a different figure than the "about 100 ms" claim above; both are TypeSafe's own words and neither page reconciles the discrepancy. [DOC] https://docs.typesafe.ai/concepts/use-case-map
- TypeSafe states a target of "a greater than 100x intelligence-to-speed-and-cost ratio," framed as a bet that cheaper intelligence creates more demand. [DOC] https://docs.typesafe.ai/concepts/how-to-build-with-system-one
- Question/answer pairs are described as "primitives": modular, composable, structured, reliable, fast. Every answer is constrained to the options you supplied (never a value outside them), and every question in a request is evaluated independently and in parallel, so one answer is never hidden context for another. [DOC] https://docs.typesafe.ai/introduction and https://docs.typesafe.ai/primitives

## 2. The three primitives

All three question types share `type` and `instructions`; each adds its own `criteria`. [DOC] https://docs.typesafe.ai/api

### Choice
Request fields: `type` ("choice", required), `instructions` (string, object, or array, required, what the model should decide), `criteria` (map<string, string|null>, required: a map of option name to rubric description; use null when an option needs no extra detail; up to 255 options). [DOC] https://docs.typesafe.ai/api and https://docs.typesafe.ai/primitives/choice
Response fields: `type`, `choice` (the highest-probability option), `probabilities` (map<option, number> summing to 1), `confidence` (0 to 1, derived from probabilities). [DOC] https://docs.typesafe.ai/api
Recommended when: the answer is one of a fixed set of options with no order between them (routing, document type, programming language detection). [DOC] https://docs.typesafe.ai/primitives/choice
Verbatim request example:
```json
{
  "state": "Help! My payouts have been failing for 3 days.",
  "model": "jev-latest",
  "questions": {
    "department": {
      "type": "choice",
      "instructions": "Which team should handle this?",
      "criteria": {
        "billing": "Payments, invoicing, refunds",
        "technical": "Bugs, outages, integrations",
        "sales": "Pricing, upgrades, new accounts"
      }
    }
  }
}
```
[DOC] https://docs.typesafe.ai/api
Verbatim response example:
```json
{
  "model": "jev-latest",
  "answers": {
    "department": {
      "type": "choice",
      "choice": "technical",
      "probabilities": { "billing": 0.08, "technical": 0.85, "sales": 0.07 },
      "confidence": 0.82
    }
  },
  "usage": { "input_tokens": 312, "output_tokens": 48 }
}
```
[DOC] https://docs.typesafe.ai/api

### Score
Request fields: `type` ("score", required), `instructions` (required, what the model should rate), `criteria` (ordered array, required; at least two levels, up to 10). [DOC] https://docs.typesafe.ai/api and https://docs.typesafe.ai/primitives/score
Response fields: `type`, `score` (probability-weighted position across levels, can land between two levels; computed as each level number times its probability, summed), `legend` (level number to description), `probabilities` (map<level-as-string, number> summing to 1), `confidence` (0 to 1). [DOC] https://docs.typesafe.ai/api and https://docs.typesafe.ai/primitives/score
Recommended when: the answer is a position on a describable spectrum (bug severity, customer frustration, candidate skill level). [DOC] https://docs.typesafe.ai/primitives/score
Verbatim request example:
```json
{
  "state": "Help! My payouts have been failing for 3 days.",
  "model": "jev-latest",
  "questions": {
    "frustration": {
      "type": "score",
      "instructions": "How frustrated is the customer?",
      "criteria": ["Calm", "Frustrated", "Very angry"]
    }
  }
}
```
[DOC] https://docs.typesafe.ai/api
Verbatim response example:
```json
{
  "model": "jev-latest",
  "answers": {
    "frustration": {
      "type": "score",
      "score": 1.6,
      "legend": { "0": "Calm", "1": "Frustrated", "2": "Very angry" },
      "probabilities": { "0": 0.05, "1": 0.3, "2": 0.65 },
      "confidence": 0.78
    }
  },
  "usage": { "input_tokens": 312, "output_tokens": 48 }
}
```
[DOC] https://docs.typesafe.ai/api

### Noul
Request fields: `type` ("noul", required), `instructions` (the yes/no question or statement, required), `criteria` (optional object with `true`/`false` string descriptions clarifying what a yes and a no mean). [DOC] https://docs.typesafe.ai/api and https://docs.typesafe.ai/primitives/noul
Response fields: `type`, `noul` (single number 0 to 1, the probability the answer is yes). Noul answers carry no separate `confidence` field. [DOC] https://docs.typesafe.ai/api and https://docs.typesafe.ai/primitives/noul
Recommended when: the answer is a clean yes/no where the probability itself is the useful signal (does this request a refund, does this contain PII). [DOC] https://docs.typesafe.ai/primitives/noul
Verbatim request example:
```json
{
  "state": "Help! My payouts have been failing for 3 days.",
  "model": "jev-latest",
  "questions": {
    "is_urgent": {
      "type": "noul",
      "instructions": "Does this convey urgency?",
      "criteria": {
        "true": "Explicitly time-sensitive",
        "false": "No urgency expressed"
      }
    }
  }
}
```
[DOC] https://docs.typesafe.ai/api
Verbatim response example:
```json
{
  "model": "jev-latest",
  "answers": { "is_urgent": { "type": "noul", "noul": 0.92 } },
  "usage": { "input_tokens": 312, "output_tokens": 48 }
}
```
[DOC] https://docs.typesafe.ai/api

### How to choose between them
"Use Noul for a yes/no judgment and Score to measure a position on a spectrum... A Noul value of 0.5 means the model gives yes and no equal probability. It does not mean the candidate has a medium skill level." If two types both seem to fit, prefer the one whose answer your code can act on directly. [DOC] https://docs.typesafe.ai/primitives

## 3. Probability versus confidence

- Definition: `probabilities` is the full probability distribution over the options (Choice) or levels (Score) you supplied, and it always sums to 1. `confidence` is a single number from 0 to 1 that "collapses that shape into a single number," computed by TypeSafe from the same probability distribution, so a concentrated (peaked) distribution yields high confidence and a flat/spread distribution yields low confidence. Noul answers carry no `confidence` field. [DOC] https://docs.typesafe.ai/confidence
- TypeSafe explicitly frames `confidence` as one convenient default, not the only valid measure: "We provide `confidence` as a convenient measure that fits most use-cases, but you are never locked into our definition... which is exactly why we give you the full `probabilities` in the response." A promised future cookbook on alternative confidence computations is referenced but not yet published (the docs say "we'll add the link here when we do"). [DOC] https://docs.typesafe.ai/confidence
- How it is calibrated: Jev is trained with a method TypeSafe calls RLCD (reinforcement learning for calibrated decisions), positioned as a third post-training path alongside RLHF and RLVR. Under RLCD "the model does not generate text," "it returns decisions and probabilities," and "higher probability should correspond to a greater chance that the answer is correct." [DOC] https://docs.typesafe.ai/introduction/machine-learning-primer
- Calibration claim (definitional, not a measured benchmark number): "Across many predictions from a well-calibrated model: Outcomes assigned a probability of 0.2 should occur about 20% of the time. Outcomes assigned a probability of 0.8 should occur about 80% of the time. Outcomes assigned a probability of 1.0 should occur 100% of the time. These rates describe groups of predictions, not a guarantee about any single answer." [DOC] https://docs.typesafe.ai/introduction/machine-learning-primer
- No fetched page publishes a calibration curve, ECE/Brier score, or accuracy-vs-confidence measurement for Jev. The closest published numbers are repeatability (self-consistency across repeated calls), not calibration or ground-truth accuracy, and the self-consistency cookbooks explicitly disclaim that they measure accuracy: "None of this shows accuracy or superiority: Haiku at temperature 0 had 100% agreement [with itself]..." [DOC] https://docs.typesafe.ai/cookbooks/consistency_choice_cookbook
- Repeatability numbers (self-consistency, choices): over 15 repeats of an 8-question Choice rubric on one moderation post, "the LLM distribution settings repeat their plurality labels 87.5% to 100% of the time, compared with TypeSafe's 90.8%." Requiring a top probability of at least 0.60 (else the result is "uncertain" and goes to human review) raised TypeSafe's agreement to 99.2%, with 74.2% of answers acted on automatically and 25.8% marked uncertain. Under the same 0.60 rule, one LLM condition (Haiku at temperature 0) scored 100% repeatability, which the docs caveat as not implying correctness. [DOC] https://docs.typesafe.ai/cookbooks/consistency_choice_cookbook
- Repeatability numbers (self-consistency, nouls): over 15 repeats of a 14-question Noul rubric on one insurance claim, "TypeSafe's mean per-question probability standard deviation is 0.0102, below all LLM probability conditions" tested (which included Claude Haiku 4.5, GPT-5.4-mini at temperature 0 and default, and reasoning models GPT-5.5 and Claude Opus 4.8). Its "covered" answers spanned 0.43 to 0.53, crossing a 0.5 decision threshold. [DOC] https://docs.typesafe.ai/cookbooks/consistency_noul_cookbook
- Recommended thresholding approach: divide confidence into three bands, each producing different system behavior: high confidence (act automatically), medium confidence (proceed with caution: confirm, flag, or gather more information), low confidence (do not act: route to a human, ask for clarification, or fall back to a different system). "Where you draw those boundaries depends on the stakes." [DOC] https://docs.typesafe.ai/confidence
- Thresholds scale with risk, not one global number: "Different actions within the same system should be gated at different levels depending on the consequences of getting it wrong." A worked example uses a 0.5 floor for "genuinely unsure," then a higher bar (e.g. greater than 0.9) for a destructive/high-stakes action versus a lower bar for a low-stakes, easily-recoverable one. TypeSafe explicitly says "the correct threshold values depend on your domain and the performance of the model for your use case. Start with conservative thresholds, test with your own data, and adjust as you observe results." [DOC] https://docs.typesafe.ai/confidence and https://docs.typesafe.ai/patterns/confidence-routing
- Practical guidance from the agent-skill page: "If all you care about is choosing the best option, you just need to choose the option with the highest confidence (rather than setting a confidence threshold). If you have a specific statistical algorithm in mind, you should probably be using probabilities instead of confidence." [DOC] https://docs.typesafe.ai/agent-skill
- Do not assume structural equivalence across question framings: a Noul's `noul` value and a two-option Choice's `probabilities["yes"]` value answered the same underlying question but returned very different numbers in a worked example (noul 0.22 vs Choice yes-probability 0.01, confidence 0.97), and a Noul and its literal negation as a second Noul did not sum to 1 in another example (0.72 and 0.47, summing to 1.19). TypeSafe's guidance: "don't rely on expected structural invariance... don't carry a threshold tuned on a Noul over to a Choice, and don't hold the model to arithmetic identities between separate questions." [DOC] https://docs.typesafe.ai/model-jaggedness/jev-1.13

## 4. Patterns and cookbooks

### The four named patterns (https://docs.typesafe.ai/patterns)
- Speculative Fan-Out: send many questions (including speculative ones that may not end up relevant) in a single call, and let code decide what's relevant after the fact. Benefit: cost, speed. Recipe: ask every question your code might need against the same state in one request; questions run in parallel so adding questions "barely changes the response time." A support-ticket example sends `category`, `bug_severity`, `has_reproducible_steps`, `refund_requested`, and `frustration` together, then code ignores whichever speculative answers don't apply to the ticket's actual category. [DOC] https://docs.typesafe.ai/patterns/fan-out
- Confidence-Gated Routing: use `confidence` as a second axis alongside the answer itself. Benefit: reliability, safety. Recipe (voice-banking example): a hard floor (e.g. below 0.6 confidence, always route to a human) with per-action thresholds set by stakes (checking a balance needs only 0.6; approving a transfer needs greater than 0.85, else ask the user to confirm). [DOC] https://docs.typesafe.ai/patterns/confidence-routing
- Composite Scoring: break a complex judgment into independent atomic Score questions, then combine them with weights you control in code. Benefit: cost, reliability, speed. Recipe (resume screening): score `python_depth`, `team_leadership`, `system_design`, `generalist` independently (each on a 0 to 4 scale), normalize each to 0 to 1 by dividing by its top level number, then combine with role-specific weights, e.g. `ic_score = 0.40*py + 0.10*lead + 0.40*arch + 0.10*general`. The weights live in your code so a mismatch between ranking and expectation is fixed by adjusting a weight, not rewriting a prompt. [DOC] https://docs.typesafe.ai/patterns/composite-scoring
- Intent Routing: classify a request's intent (and optionally complexity) and route each to a deterministic handler, a specialist LLM, or a human. Benefit: cost, speed. Recipe (customer service): one Choice for `intent` plus one Score for `complexity`; low confidence on intent routes to a human; certain intents go straight to code, others to a specialist LLM, and complaints route to a human when either complexity or confidence is unfavorable. [DOC] https://docs.typesafe.ai/patterns/intent-routing

### Cookbooks (recipe, measured numbers as published, caveats)

- Self-consistency: nouls. Recipe: run a 14-question Noul rubric 15 times per condition (TypeSafe vs several LLMs at various settings) on one auto-insurance claim, and map probabilities in [0.30, 0.70] to an explicit "uncertain" outcome for human review instead of forcing yes/no at a 0.5 line. Measured: "TypeSafe's mean per-question probability standard deviation is 0.0102, below all LLM probability conditions here. Its covered answers span 0.43 to 0.53, crossing a 0.5 decision threshold." Caveat: "The band is illustrative; it is neither a calibrated guarantee nor an optimized threshold. Set production boundaries from labeled examples and from the cost of incorrect decisions and of review." Also: "A value near either outer boundary can still move between uncertain and yes or no. The model is no more deterministic for it, and an automatic decision that clears the band is not shown to be correct." [DOC] https://docs.typesafe.ai/cookbooks/consistency_noul_cookbook
- Self-consistency: choices. Recipe: run an 8-question moderation Choice rubric 15 times per condition on one borderline post; add an "uncertain" outcome gated on top probability greater than or equal to 0.60. Measured: plurality-label repeatability 87.5% to 100% for LLM conditions vs 90.8% for TypeSafe raw; with the 0.60 gate, TypeSafe rose to 99.2% agreement with 74.2% automatic / 25.8% uncertain; TypeSafe flips label on 2 of 8 questions across repeats; "primary_risk" and "link_handling" came back uncertain on every repeat. Caveat, verbatim: "None of this shows accuracy or superiority: Haiku at temperature 0 had 100% agreement... This experiment does not measure accuracy." [DOC] https://docs.typesafe.ai/cookbooks/consistency_choice_cookbook
- Parallel questions. Recipe: batch a 13-question regulatory briefing about the GDPR Wikipedia article into one TypeSafe call instead of 13 separate calls. Measured: "batching every question into one TypeSafe call is 12.2x cheaper and 10.0x faster with no change in the answers." [DOC] https://docs.typesafe.ai/cookbooks/parallel_questions
- Re-ranking. Recipe: build 30-passage BM25 shortlists for 40 CLERC legal queries, then ask one TypeSafe Choice question per query-candidate pair to re-rank. Measured: top-1 accuracy rose from 5% (BM25 alone) to 18%; top-5 from 15% to 35%; top-10 from 38% to 62%. Caveat: the right passage is present in the shortlist 100% of the time but is rarely ranked first by search alone (only 5%), which is the gap re-ranking closes. [DOC] https://docs.typesafe.ai/cookbooks/rerank_typesafe
- Line-by-line search (semantic find). Recipe: tag every line of a document (GitHub's Terms of Service, 218 lines) with an ID; one Choice question ranks all 218 line IDs against a plain-language query in a single request; a companion Noul question checks whether the document actually contains an answer at all ("exists"). Measured examples: for an "arbitration" query the top-ranked line scored 0.86 relevance but `exists` was only 0.14, meaning the answer is not in the document; for a "parental permission" query the top line answered a related-but-different question, so the result was flagged as "partially addressed." Caveat: "The ranking tells you where to look; the exists score tells you whether the result answers the question." [DOC] https://docs.typesafe.ai/cookbooks/semantic_find
- Structure recovery (autoformat). Recipe: reconstruct Markdown structure from plain hard-wrapped text in two sequential requests: pass 1 asks one Noul per adjacent line pair ("does this line pick up mid-sentence?") to decide where to merge lines into blocks; pass 2 asks one Choice per merged block (heading/paragraph/list/quote/code/callout) plus type-specific companion questions. Measured: for the worked memo, two round trips, 10,211 tokens total, 0.8 seconds, and a stated cost of "$0.0015" for the whole document (the code's own printed cost figure in that run was $0.0003; the two figures appear together in the text without reconciliation). Caveat/lesson: asking "are these lines part of the same paragraph?" instead of "does this line pick up mid-sentence?" merged unmarked list items into surrounding prose (12 blocks recovered vs the correct 17), because "picking up mid-sentence" is a narrower, more literal fact than "same paragraph." The lowest-confidence block in the worked example split its probability across three plausible types (paragraph 0.53, list_item 0.24, callout 0.19), which the docs suggest surfacing in a UI for review below a confidence threshold such as 0.55. [DOC] https://docs.typesafe.ai/cookbooks/autoformat
- Function calling. Recipe: map a natural-language trading request onto ordinary typed Python functions whose arguments are `Literal` enums, by turning each closed-set argument into a Choice question with confidence. Measured examples (illustrative, not a benchmark): "plot rolling correlation between nvda and spy for the past month" to `rolling_correlation(...)` at confidence 0.91; "compare nvda amd and msft..." at confidence 0.94; "show me apple daily with volume" at confidence 0.75; "what tickers do you have" (no arguments) at confidence 1.00. [DOC] https://docs.typesafe.ai/cookbooks/function_calling
- Skill suggestion. Recipe: rather than truncating and loading all 182 skills from Nous Research's Hermes catalog into an agent's system prompt, run two TypeSafe requests per turn: the first ranks every skill against the turn and decides whether a skill is needed at all; the second re-reads only the top three candidates in full and can reject all of them; the winner's name is injected as one line of the system prompt. Measured over 488 requests against claude-haiku-4-5-20251001: wrong-skill loads fell from 16.8% (agent alone) to 7.3% with a TypeSafe suggestion (2.3x fewer), and needless loads (loading a skill when none was needed) fell from 9.8% to 4.0% (2.4x fewer); an "oracle" ceiling (agent handed the correct answer directly) still showed 2.5%/1.2% error, described as "the floor for making mistakes is not zero... no selection method, however good, gets past" the agent's own residual error. Of 315 "covered" requests, the suggestion fixed 37 that the agent got wrong alone but broke 7 the agent had right alone. Caveat, verbatim: "A confident wrong suggestion is more persuasive than no suggestion at all, which is the price of putting one in front of the turn." [DOC] https://docs.typesafe.ai/cookbooks/skill_suggestion
- Knowledge graph entity alignment. Recipe: instead of thresholding a Noul or losing order in a Choice, use one Score question with exactly three levels mapped to the three real actions available (leave unlinked / send to a curator / merge), plus companion Noul questions per compared field to help the curator on ambiguous pairs. Measured: over 450 candidate beer-catalogue pairs, the rounded Score placed 8.9% as an asserted same-entity merge, 11.1% into a curator queue, and 80.0% as left unlinked. Design point, verbatim: "There is no threshold to fit," because the three Score levels already correspond to the three possible code actions. [DOC] https://docs.typesafe.ai/cookbooks/entity_alignment
- Classifying RAG passages. Recipe: between retrieval and generation, send one request per retrieved passage carrying four Noul questions (relevant? states usable evidence? contradicts the query's premise? contains a prompt injection or instruction?), then route each passage in code with ordered threshold tests: `contains_prompt_injection > 0.70` excludes first (a security decision, not an evidence one), then `contradicts_query_premise > 0.70` routes to a "conflicting evidence" block, then `is_relevant < 0.45` excludes, then `contains_answer_evidence > 0.55` includes, else exclude. Worked examples show a top-similarity-ranked passage excluded at `is_relevant`=0.71 because `contains_prompt_injection`=0.99, and a passage with only 0.49 relevance / 0.51 evidence still routed to "conflicting evidence" because it scored 0.92 on contradicting the query's premise. Caveat: "The injection question is a filter, and only one. A passage that scores under the threshold still reaches the prompt, so the generator prompt has to treat every passage as untrusted text regardless of its score. Nothing here is a security boundary." Cost note: "One request per passage, so cost scales with k." [DOC] https://docs.typesafe.ai/cookbooks/classifying_rag_passages
- Double-checking citations. Recipe: for each citation, first do an ordinary string match for the quoted text against the source; if the quote isn't found, mark it "fabricated" without ever calling the model; if found, ask one Choice question ("supports"/"contradicts"/"says_nothing") over the claim and the quote's surrounding section, mapped to verdicts verified/contradicted/unsupported, gated on confidence greater than or equal to 0.8 to auto-accept versus send to a human. Measured, worked example (8 citations about RFC 7519): 4 verified at confidence >= 0.93; 1 fabricated (caught by string match alone, never reached the model); 1 contradicted at confidence 0.99 (quote was accurate, section 4.1.4 contradicted the claim built on it); 2 unsupported at confidence 0.27 and 0.56, both sent to review. Caveat: the string match is exact after normalization, so a truncated or lightly reworded quote is reported as "fabricated" even if the true source exists; fuzzy matching would be needed for sloppier quoting. [DOC] https://docs.typesafe.ai/cookbooks/citation_check
- Guardrails for LLMs. Recipe: screen every LLM input and output with one TypeSafe request per message: one Noul per named hazard (jailbreak, policy-breaking reply, harmful request, medical advice, self-harm) plus one Score for overall severity of harm from complying; a named "policy" (a dict of numbers) decides action per hazard (block/review/support), with two independent thresholds (an "action threshold" that triggers the hazard's mapped action, and a lower "review threshold" that sends the message to a human) plus a severity threshold that can escalate a review into a block. Measured, worked example: the same TypeSafe assessment (jailbreak probability 0.74, severity 0.51) was routed to "block" under a "strict" policy (action threshold 0.70) but only to "review" under a "permissive" policy (action threshold 0.85), demonstrating that "TypeSafe supplies the assessment; your application owns the decision." [DOC] https://docs.typesafe.ai/cookbooks/llm_guardrails
- SDE cascade. Recipe: a two-stage structured-data-extraction cascade: (1) extract with a cheap/small text model, (2) verify with a battery of per-field TypeSafe Noul questions asking "is this value wrong" style questions, (3) escalate to an expensive reasoning model only when a verifier signal fires, else keep the cheap answer. Priced example models: mini extraction rung at $0.75/$4.50 per 1M tokens (in/out); reasoning escalation rung at $5.00/$30.00 ("roughly 7x the mini"); the TypeSafe verifier itself at $0.042/$0.00 (jev-1.12, output free). Measured: "internal TypeSafe results" over 100 scrapegraphai prompts show the cascade's cost/quality Pareto frontier sitting "up-and-left of every single model" tested standalone; the strongest standalone model (gpt-5.5-reasoning) sits at roughly 0.81 quality for roughly $0.10 per extraction, and sweeping the cascade's escalation-gate threshold buys "most of the top model's quality at a fraction of its cost." Caveat, verbatim: "the chart is a historical snapshot; its costs have not been recalculated at the current Jev rate listed above," and it is explicitly labeled "internal TypeSafe results," not an independently reproduced benchmark. [DOC] https://docs.typesafe.ai/cookbooks/sde_cascade
- Date extraction. Recipe: because Jev is unreliable at date arithmetic, extract each date's components (month, day, year, relative reference) as bounded Choice questions (each is a small closed set) with an explicit "not stated" option, then assemble, compare, and validate dates in code, never in the model. Route on confidence, where "a date's confidence is the lowest one among the parts that went into it" and a date under a 0.60 review floor (or one code could not assemble at all) goes to a human. Measured, worked example: of 6 example documents, 5 were auto-accepted and 1 ("the date of the kickoff call") was sent to review at confidence 0.46, flagged "absolute date incomplete." [DOC] https://docs.typesafe.ai/cookbooks/date_extraction_cookbook
- Pre-parsed value extraction. Recipe: a regex finds candidate spans in text (emails, phone numbers, amounts, tuned to over-find), a TypeSafe Choice question picks which candidate answers the question (plus any attribute needed downstream, such as currency or credit-vs-charge), and code copies the picked span verbatim and normalizes it; because the model can only choose among regex-found spans, it cannot invent a value or transpose a digit. Two stated limits: a Choice question allows at most 255 options, so with more candidates than that you must narrow in two stages (pick the section, then the span inside it); and finding candidates is the hard part for anything without a good regex (a person's name, for example), which needs a roster, an NER system, or an LLM to propose candidates first. [DOC] https://docs.typesafe.ai/cookbooks/pre_parsed_value_extraction_cookbook
- Hierarchical classification. Recipe: classify into deep taxonomies (patent codes, retail categories, biomedical subject headings, source-code directories) by walking one Choice question per tree level, keeping the top K candidate paths alive with a beam search over Choice probabilities rather than committing greedily to one path per level. Measured: across 4 worked examples (CPC patents, Shopify products, MeSH biomedical subjects, a codebase's own files), "Beam search matched 4 of 4 expected leaves; greedy search matched 2 of 4." The two cases greedy search missed were ones where the correct branch was not the single highest-probability branch at an early level, but was recovered by keeping K=3 candidate paths alive. [DOC] https://docs.typesafe.ai/cookbooks/hierarchical_classification
- Autoresearch feature discovery. Recipe: an iterative loop where an LLM proposes candidate TypeSafe questions about free text (a wine tasting note), TypeSafe answers all of them for every row (a Score answer becomes two numeric columns, its mean level and its spread; a Noul answer becomes one probability column), a supervised CatBoost regressor trains on those columns, and the next proposal round reads the model's error report to refine which questions to keep asking. Measured: 2,000 wine reviews, 38 accepted TypeSafe questions producing 67 numeric columns, held-out RMSE of 1.77 points on an 80-100 critic-score scale; the largest single feature-importance share among the 38 questions was "note_overall_tone_positivity" at 17.4% of total CatBoost feature importance (importance is normalized so all questions sum to 100%; it is explicitly not a share of rows, of questions, or of prediction accuracy). [DOC] https://docs.typesafe.ai/cookbooks/autoresearch_feature_discovery
- Classification using confidence. Recipe: classify SEC annual-report filings into 75 industry groups with one Choice question, then use the answer's own `confidence` (not the raw probability of the chosen label) to decide whether to report the narrow group or step up to its broader division in a known label hierarchy, at zero extra API cost since the broader label is derived in code from the narrow one. Measured: over 60 filings, a confidence cutoff of 0.9 split the set roughly in half; "the confident half is right 90% of the time; the other half, 40%. Reported one level up, that 40% becomes 70%." Caveat: labels are self-reported by filers and can go stale, so "these 60 were filtered down to filings whose own text supports the code they carry" and the docs say the resulting numbers "measure the recipe rather than the state of EDGAR's metadata." [DOC] https://docs.typesafe.ai/cookbooks/classification_using_confidence

## 5. Advanced structure: instructions, options, levels, criteria

- Every one of `instructions` (Choice, Score, Noul), Choice `criteria` option descriptions, Score `criteria` level descriptions, and Noul `criteria.true`/`criteria.false` accepts a string, an object, an array, or null. [DOC] https://docs.typesafe.ai/primitives/advanced
- When to add structure: "when it helps with clarity" for a multi-part question (labeled JSON keys beat a dense prose string), and "when a question needs supporting data" that is already JSON (a schema, taxonomy, or database row), where you can pass the relevant subfields directly instead of serializing them into a string template. [DOC] https://docs.typesafe.ai/primitives/advanced
- A common structured pattern for Choice options that are easy to confuse: give each option an object with parallel fields such as `what` (what the option covers), `not_for` (what belongs to a neighboring option instead), and `examples` (representative inputs); using the same field names across every option lets the model compare them directly. [DOC] https://docs.typesafe.ai/primitives/advanced and https://docs.typesafe.ai/primitives/choice
- Score levels can similarly become objects with a `what` and an `examples` field per level; in one worked A/B test, adding a matching example moved a bug report's score/confidence from 1.30/0.54 (plain string levels) to 1.07/0.90 (level with a relevant example), while an unrelated example barely moved it (1.28/0.57), which TypeSafe reads as evidence that "examples steer the model, and they only help when they look like your real inputs." [DOC] https://docs.typesafe.ai/primitives/score
- Walking a deep taxonomy: ask one Choice per tree level, where the options at each step are the current node's children and each option's description is that child's own subtree, so the model can see what lives further down a branch before committing to it; combine with a beam search (see the Hierarchical Classification cookbook) rather than a single greedy path when branches are close in probability. [DOC] https://docs.typesafe.ai/primitives/advanced and https://docs.typesafe.ai/cookbooks/hierarchical_classification
- Field names you invent inside a structured `instructions` or `criteria` object (e.g. `question`, `focus`, `what`, `not_for`, `examples`) are not part of the API and none are reserved; the model sees the names along with the values, so short, descriptive names are recommended. [DOC] https://docs.typesafe.ai/primitives/choice

## 9. Known limitations and failure modes they admit

All from the dedicated "Jev 1.13 jaggedness" page, last reviewed 2026-09-17 per the page itself: [DOC] https://docs.typesafe.ai/model-jaggedness/jev-1.13

1. Literal reading: "answers the question you wrote, not the one you meant." Scoping words, negations, and implied conditions are read at face value. Fix: state the exact condition in `instructions`; put boundary cases in `criteria`; split unavoidable interpretation into two literal questions combined in code.
2. Math and numbers: "Jev is not a calculator... implement any mathematical logic in code." Sub-cases: counting is unreliable and the error grows with the size of what's being counted (fix: iterate in code, ask one Noul per candidate item, sum in code); numeric representations underperform semantic ones (hex colors worse than English color names; low-level/assembly code worse than high-level code; fix: convert to a named bucket in code first); Score outputs should not be used to reconstruct an exact interpolated numeric value between two levels, only to threshold.
3. Date and time comparison: dates are read "as text, not as ordered quantities"; ordering, duration, and window membership are unreliable, worse with mixed formats and domain-specific boundaries. Fix: extract components as a bounded Choice (small closed sets: 12 months, 31 days, a bounded year range, with an explicit "not stated" option), then do all comparison arithmetic in code.
4. Indirection: instructions with double negatives or multi-hop "property of a property" reasoning cost accuracy. Fix: write instructions as directly as possible and name relevant state parts explicitly.
5. Large state full of irrelevant detail: accuracy falls as state grows with unrelated content, described elsewhere on the same page as Jev "suffer[ing] from context rot." Fix: filter/retrieve in code first and send only what the question needs; when code-side filtering isn't possible, use a Noul question to filter for relevance first (see the Classifying RAG Passages cookbook).
6. Adversarial content: "State is data, and jev-1.13 does not treat it as hostile by default." Injected instructions, misleading framing, or self-arguing text can move the answer; TypeSafe says it expects to improve this in future versions. Fix: be explicit in criteria and test thoroughly before deploying.
7. Contradictory instructions and criteria: when `instructions` and `criteria` point in different directions (e.g. a Noul whose "true" criterion actually describes a no), performance drops. Fix: treat criteria as an extension of the instruction and align the two in plain, unambiguous language.
8. Common-sense structural invariants are not guaranteed: outputs are "extremely consistent" for semantically similar inputs, but there is no guaranteed arithmetic relationship between a Noul's probability and an equivalent Choice's probability for the same underlying question, nor between a Noul and its literal negation asked as a second Noul (documented mismatches: noul 0.22 vs a Choice yes-probability of 0.01 for what the docs treat as comparable questions; a Noul/negated-Noul pair summing to 1.19 instead of 1.0). Fix: don't rely on structural invariance between separately-asked questions; word each question to mean exactly what you want.
9. Generation: "jev-1.13 is not trained to generate text." You can force text generation by chaining Choices, but "this will not work well and will be very slow." Fix: for extraction, turn the answer space into a bounded Choice over candidate values (found by regex or another model) rather than asking Jev to generate the value itself; for genuine free-text generation, use a different (generative) model.

Summary warning box on the same page, verbatim as a checklist of things to avoid: "Asking the model something code can compute exactly. Hiding several judgments inside one question. System Two tasks: more layers of indirections[.] Giving it more context in state than the question needs. Jev suffers from context rot, so unrelated material in the state costs you accuracy." [DOC] https://docs.typesafe.ai/model-jaggedness/jev-1.13

## 10. Ten most useful concrete facts for deciding WHERE Jev beats a text-model judge, and where it should not be used

OPINION (synthesis by this research agent, built on the facts cited above; not TypeSafe's own framing):

1. Jev is built and priced for narrow, atomic, closed-answer judgments evaluated against a supplied state, not for open-ended reasoning or free text generation; a text-model judge is still the right tool whenever the task genuinely needs generated prose, multi-step chained reasoning, or "why" explanations, since Jev "is not trained to generate text" and degrades on multi-hop indirection (sections 1, 9).
2. Its per-input economics are extreme relative to a general LLM judge: $0.042 per million input tokens with free output, versus the SDE cascade cookbook's own comparison rung priced at $5.00/$30.00 per million for a reasoning model (roughly 100 to 1,000x cheaper per token depending on the comparison point), which is the strongest argument for routing high-volume, low-stakes classification/scoring work to Jev first and reserving an expensive model only for what Jev's own confidence or a verifier flags (sections 4, 6).
3. Batching many questions into one call is close to free in both cost and latency (12.2x cheaper, 10.0x faster in the measured 13-question example, with no change in answers), so any orchestrator design should default to speculative fan-out (ask everything that might matter in one request) rather than one question per call, which is the opposite instinct from how people usually prompt an LLM judge (section 4).
4. `confidence` is a genuinely different control surface than anything a text-model judge exposes for free: it is a calibrated-by-training, per-answer number you can threshold in code to gate automatic action vs. human review vs. escalation, and TypeSafe's own worked examples (SEC filings, RAG passage routing, guardrails) show real accuracy gains from reading it rather than just the top label (90% vs 40% accuracy split by a 0.9 confidence cutoff in one cookbook) (sections 3, 4).
5. Jev is measurably more repeatable across identical repeated calls than the general LLMs TypeSafe benchmarked against it (mean Noul probability standard deviation of 0.0102 vs higher for every tested LLM condition; 99.2% plurality-label agreement with an uncertainty gate vs 84.2 to 94.2% for most LLM conditions), which matters specifically for any pipeline where the same input being scored twice must not silently change the outcome; but TypeSafe explicitly disclaims that this repeatability data says anything about ground-truth accuracy, so it should not be quoted as an accuracy claim (section 3).
6. Jev is explicitly bad at anything that is really a code problem wearing a judgment costume: counting, date/time arithmetic, numeric interpolation from Score outputs, and hex/binary/low-level representations. Any orchestrator brief should route those to deterministic code, not to Jev and not to a text-model judge either; this is a place where "beats a text-model judge" is the wrong frame entirely (section 9).
7. Jev treats its input state as data, not as a trust boundary, and does not resist adversarial or injected content by default; it should not be the last line of defense in a security-sensitive filter without a companion boundary (e.g. treating every passage as untrusted downstream regardless of score, as the RAG-passage cookbook's own caveat states) (sections 4, 9).
8. Context/state size matters more for Jev than it typically does for a large modern LLM judge: TypeSafe describes "context rot" as an active failure mode and recommends filtering/retrieving before sending state, within a hard budget of about 64k tokens total (32k per the OpenRouter listing), well below what many frontier text-model judges can hold; large, noisy, loosely-relevant context is a reason to prefer a text-model judge or a pre-filter step instead (sections 1, 6, 9).
9. Jev is a poor fit for anything requiring a hierarchy or hard cap it can't natively express in one call: Choice tops out at 255 options and Score at 10 levels, so deep taxonomies need a multi-step beam search (the hierarchical classification cookbook shows this working well, 4/4 vs greedy's 2/4, but it is real engineering, not a single API call) (sections 2, 4, 6).
10. Data-handling claims are narrower than they might first appear: TypeSafe commits only to "not trained on customer requests or responses" and "not fine-tuned... with customer data," offers ZDR only to enterprise customers on request, and is silent on data region/locality and on whether logged traffic is used for any other internal purpose; an orchestrator handling sensitive data should treat anything beyond the two explicit denials as unconfirmed rather than assume a broader privacy posture, and should not assume OpenRouter routing (which this digest could not confirm TypeSafe documents at all) carries the same data-handling terms as the native API (sections 7, 8).
