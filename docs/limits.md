# What the guards do not cover

This page says what Brother's command guards refuse, how often they refuse an ordinary command, how to switch each one off, and what they cannot see. It is a reference, and every claim on it is narrow on purpose: a guard reads the text of a command, and text does not show everything a command will do.

## How often a harmless command is refused

The Bash guard was run over the benign corpus in `scripts/benign_corpus.json`: ordinary commands taken from public documentation, each row with its source address. It refused none of them.

0 denials over the 200 shell rows and 60 zh or ja rows bound the false park rate to about 1.5 and 5 percent at 95 percent confidence. The bound is the rule of three (3 divided by the number of rows), an estimate: it assumes the rows are independent draws from the commands a stranger runs, and the corpus is a sample, not that population. It says nothing about a command shape the corpus does not hold, and the corpus holds no here-document. A here-document body (the lines after `<<TAG`, `<<-TAG`, `<<'TAG'` or `<<"TAG"` up to the line that is exactly TAG, or to the end of the text when the terminator is missing) is treated as data: an apostrophe in it is not an unterminated quote and a line in it that looks like a command is not one. The command line that carries the `<<` is still judged, and so is any command after the terminator. Two exceptions read the body: a body fed to curl, wget or nc on stdin is refused when it looks like a secret (a private key block, a token prefix, or a NAME=value line whose name says secret), and a body that a shell reads from stdin (`bash <<EOF`, `cat <<EOF | sh`) is judged as commands. A here-document inside a double-quoted `$(...)` is not recognised, because the quote scanner takes the whole string first; a body there with an odd number of double quote characters can still make the command unsplittable, and it is then refused.

`scripts/test_guards_for_strangers.py` recomputes both figures from the corpus on every run, so adding rows moves the numbers that checker expects, and this page must move with them.

## What the Bash guard refuses

- An upload of a secret shaped file by curl or wget (`-d @.env`, `--data-binary @f`, `-T f`, `-F x=@f`, `--post-file f`), a redirect or a command substitution of such a file into a network tool, and a pipe of a command naming one into nc, ncat, curl or wget, anywhere in the pipeline. Secret shaped means .env and .env.* (not `.env.example`), ssh and tls keys, `.netrc`, a file named `credentials`, and anything under `~/.ssh` or `~/.aws` (a public `.pub` key excepted).
- An interpreter one liner (python -c, node -e, perl -e, ruby -e) that deletes a tree and whose path literal is a protected path or is outside the worktree. A literal inside `[...]` or `.get(` is a dictionary key, never a path; an argument that names HOME (`os.environ['HOME']`, `os.getenv('HOME')`, `Path.home()`, `process.env.HOME`) is a delete of HOME. A delete inside the worktree is judged exactly as `rm -rf` is; a path under the system temporary folders is allowed (never one the worktree itself sits in); a path held only in a variable (`d = tempfile.mkdtemp()`) names nothing this guard can read and is left to the Stop reconciler.
- A write to a protected control plane path. The owner's own files (`src/brothersbe/evidence.py` and its family, written either from the repository root as `products/brothersbe/...` and `bundle/runtime/hooks/brothersbe/...` or from the product folder as `src/brothersbe/...`) are protected only inside the Brother source repository, which is a git repository that tracks `products/brothersbe/src/brothersbe/policy.py`; the answer is the same from any subfolder. In any other repository `src` is an ordinary folder. The check runs `git ls-files` with the repository's own fsmonitor hook switched off.
- A command that cannot be split into words. An unterminated quote is refused (no shell would run it). A trailing backslash, a command past the size ceiling (here-document bodies not counted) or too many words is refused only when its text names a network tool or an interpreter (curl, wget, nc, ncat, socat, /dev/tcp, python, node, perl, ruby, php, bash, sh, zsh, eval); otherwise it is allowed, and the guard says on stderr that it was not checked.
- A command text handed to a shell is judged as commands, to three levels: `bash -c` (with the shell's own options skipped: `-o pipefail`, `--norc`, `--`, `-x`), `sh -lc`, `eval`, `bash <<< '...'`, `echo '...' | bash`, `bash <<EOF`, and every `$(...)` or backtick substitution, in a command or in an unquoted here-document body (a quoted delimiter and single quotes keep it literal; substitutions nested inside substitutions are read to the same depth). A text still nested deeper than that is refused, never allowed unread. Bash reserved words and openers do not hide the command: `if ...; then curl ...; fi`, `for`, `while`, `case x in x) ...`, `{ ...; }`, `! cmd`, `f(){ ...; }`, `coproc`. A `#` comment (a `#` that starts a word, outside quotes) runs to the end of its line and hides nothing on the next line.
- A write under `~/.brother/park` or `~/.brother/consent`, or one that replaces `~/.brother` itself, anywhere, in any repository. A parked call is answered by a person outside the session, and the answer is trusted only because the session cannot write there. Every write shape this page names counts (a redirect or an append, tee, cp, mv out of the folder as well as into it, install, ln, mkdir, touch, rm, dd of=, a here-document redirected there, a one liner whose literals name the folder), with HOME spelled `~`, `$HOME`, `${HOME}` or written out, a glob or a brace that reaches the folder (a brace expansion of more than 64 forms counts as reaching it, since it cannot be read), any letter case, and a cd into it followed. A command that names the folder and is not a reader (ls, cat, head, tail, grep, find without an action, and the like) is refused too, so rsync, sudo tee or a script given the path cannot write it, and so is a command that names the folder and writes a path held in a variable. The park's answer command is refused too where it would run: `brother_hook.py` together with `--answer`, and a pseudo terminal (`pty.fork`, `pty.spawn`, `os.openpty`, `script`, `expect`, `unbuffer`, `socat`) beside `--answer` or a spelling of either folder, because a pseudo terminal makes the answer command's own terminal check pass. Where it would run means the first word of each command, every word of a command run by a wrapper, a shell, a launcher or an interpreter (or of the dispatcher run by its path), one liner code, and commands handed to a shell (`bash -c`, a here-document fed to bash, a substitution). Prose that only names them (a commit message, an echo or printf string, a grep pattern, a here-document written to a file) is allowed. Reading the folders stays allowed. This rule is judged before anything else is loaded, so it fails closed.
- In the Brother source, an interpreter one liner (python -c, node -e, perl -e, ruby -e, or code an interpreter reads on stdin from a here-document, a here string or `echo ... |`) that runs another program (`subprocess`, `os.system`, `os.popen`, `os.exec*`, `execSync`, `spawnSync`, `child_process`, `system(`, `exec(`, perl or ruby backticks) and either names git anywhere outside a comment (`'g' + 'it'` counts) or touches the environment that program inherits (`os.environ`, `env=`, `process.env`, `%ENV`, `ENV[`). That call is a git command whose text this guard cannot read, because its variables may be built at run time, and such a command is refused there. A shell out to anything else, and git named only in a comment, stay allowed; a stranger's repository is not affected.
- A wrapper does not hide the command: `sudo -u root`, `env -u X`, `timeout -s KILL 5`, `exec -a x`, `doas`, `busybox`, `nice -n 5`, `xargs -a FILE`. `xargs -a` of a secret shaped file into curl or nc is an upload.

A `cd` or `pushd` is followed, so a target resolves against the folder the command runs in, only where it really takes effect: joined to what follows by `&&` or `;`, outside parentheses, not backgrounded with `&`, not in a pipe, not on one side of `||`, and its target is a directory that exists. `cd -`, `cd $X`, a cd to a missing folder, and a `popd` with nothing pushed leave the folder unknown, and an unknown folder is judged where the session began. A refusal, from this guard and from the authority hook, never lists task ids.

## How to switch each guard off

Each guard has one switch. Setting it makes that guard allow the command and say so on stderr; it never makes the guard silent.

| Guard | Off switch |
| --- | --- |
| Bash guard (this page's refusals) | `BROTHERSBE_BASH_GUARD_OFF=1` |
| Fence hook (Edit and Write against declared task scope) | `BROTHERSBE_FENCE_HOOK_OFF=1` |
| Authority hook (Edit and Write against protected instruction files) | `BROTHERSBE_AUTHORITY_HOOK_OFF=1` |

Every refusal from the Bash guard names its own switch.

## What the guards cannot see

- **Cursor.** Cursor's hooks are advisory: a park there is a notice, never a block. The refusals above are enforced where the host honours a deny (Claude Code), and are advice elsewhere until a signed-in canary shows Cursor denying.
- **Egress.** Outbound traffic goes through a proxy that allows by host. Content sent to an allowed model host under another account's key is not seen, because the connection is TLS and the proxy does not read it. A secret sent to an allowed host is therefore not caught by the proxy, and the Bash guard catches it only where the command text shows the upload.
- **Text is not behaviour.** A script that reads a key, a binary, a path built at run time, a protocol the guard does not know, or a shell reached through another launcher is outside what command text shows. The Stop reconciler (`tools/sbe_session_reconcile.py`) inspects the changes that actually landed and is the authoritative check for writes.
- **A refusal is not proof of safety.** An allow means the command was not positively identified as one of the shapes above. It does not mean the command was read only.

## Shapes this guard does not see

These are known, not planned for tonight. A command in one of these shapes is allowed.

- Other upload tools: scp, rsync, ssh and openssl with a redirected secret, socat, `gh gist`, and a python urllib upload.
- A redirect to a network device (`> /dev/tcp/host/port`).
- Globs and brace expansion that spell a secret file (`.en?`, `.{env,x}`, `cat .en*`).
- curl options that read a file by another route: `curl -H @file`, `--variable`, `-K`.
- More interpreter names and spellings: pypy3, bun, deno, nodejs, `perl -E`, `node --eval=`, perl calls written without parentheses, and code fed to an interpreter on stdin (`python3 - <<EOF`), which is read only for the shell out and park rules above, never for a delete or a write.
- A one liner that reaches git with nothing this guard can read: a program name built from character codes or decoded at run time, run with no environment change. The Stop reconciler still judges what landed.
- A path outside the project directory, even inside the same repository, is not checked against the owner files.
- A here-document inside a double-quoted `$(...)`: the quote scanner takes the string first, so a body with an odd number of double quote characters makes the command unsplittable.
- A command text built at run time and handed to a shell: `bash -c "$(echo ...)"`, `source <(...)`, `bash <(...)`.
- Wrappers that carry a command in a string or run one for you: `env -S`, `caffeinate`, `script -q /dev/null`, `watch`, and `find -exec curl -d @{}`.
- The owner check takes its root from the project directory (the working directory when none is given), so a relative path that climbs out of a subfolder (`rm -f ../products/brothersbe/tools/sbe_bash_write_guard.py` from `docs`) is not seen as an owner file.
- Secret names outside the definition above: `.git-credentials`, `.npmrc`, docker and kube config, `.envrc`, and `.p12` files.
- Paths joined at run time: `rmtree(''.join(['.cl','aude']))` and similar. Only string literals written side by side, or with `+`, are read as one path.
- Another user's home or another spelling of home: `expanduser('~user')` and `os.environ['HOMEPATH']`.
- A `#` comment inside a quoted `"$(# ...)"`: bash 5 and bash 3.2 read it differently, so the text is judged one way only.
- In the Brother source, `git apply`, `git am`, `cherry-pick`, `revert`, `merge`, `pull <remote> <ref>` and `stash pop` or `stash apply` are refused when the content they bring in touches an owner file at all (a change to a guard is refused as well as a deletion), and when that content cannot be read before it runs (a URL, a process substitution, a here string, a missing file). A bare `git pull` with no resolvable upstream is allowed. A stranger's repository is not affected.
- The DEFAULT branch of a configured remote whose URL is a network URL (https://, ssh://, git:// or user@host:path; a path or file:// remote is judged like a local branch, and a git command run inside such a remote's folder by -C, --git-dir or a cd is refused unless it only reads) (the branch `refs/remotes/<remote>/HEAD` points at, or `main` when that ref is absent), as `origin/main`, `git pull origin main` with the ref already fetched, or the upstream of a bare `git pull` or `git merge`, may bring in changes to owner files; any other branch of the remote is judged by its content like a local one, because the session can push branches there without a pull request. The owner family guards the agent's authorship, and content on such a ref reached the repository through the owner's own pull request process, so the next session can pull a release that edits a guard; a local branch (even one named like a remote ref), a tag, a commit, a patch, a stash, or a remote named by URL is judged as above.
- In the Brother source the session does not author repository metadata that the remote tracking exemption trusts: `git remote add|set-url|rename|remove`, writes to `remote.*`, `branch.*.remote|merge`, `core.worktree`, `include*`, `url.*` config (also as `git -c`), `update-ref` or `symbolic-ref` or a push into `refs/remotes/`, a fetch or pull from a URL or path instead of a configured remote, and `--update-head-ok` are refused. `FETCH_HEAD` is exempt only when its first line names the URL of a configured remote and that remote's default branch, `git config --file` of the repository's own config is judged like `--local`, and `patch` and `gpatch` are judged exactly as `git apply`. `git branch --set-upstream-to` and `git push -u` also write `branch.*` config and are not refused.
- A fetch, pull, clone, `remote update` or `submodule update` that sets a transport variable inline (`GIT_CONFIG_*`, `GIT_SSH*`, `GIT_PROXY_COMMAND`, `GIT_EXEC_PATH`, `GIT_DIR`, `HOME`, `PATH` and the like) or carries a transport option (`--upload-pack`, `--receive-pack`, `-c`, `--config-env`, `--exec-path`, `--git-dir`, `--work-tree`) is refused in the Brother source, because each can send a fetch of a configured remote somewhere else and make the fetched ref look trusted. The default-branch exemption also reads the effective URL (`git ls-remote --get-url`, insteadOf applied) and holds only if it equals the configured network URL, and any `url.*.insteadOf` or `pushInsteadOf` key in any config scope disables it for every remote.
- A fetch-like git command that comes after an `export`, `declare`, `typeset`, `readonly` or bare assignment of a `GIT_*`, `SSH_*`, `XDG_*`, `HOME` or `PATH` variable, a `set -a`, or a `.`, `source`, `eval` or `exec` in the same command text is refused in the Brother source, because the hook cannot read the shell state it then runs under. An unrelated variable (`LANG=C`, `FOO=1`) does not trigger it.
- In the Brother source, a command whose text names a variable that redirects git (`GIT_CONFIG_*`, `GIT_SSH*`, `GIT_PROXY_COMMAND`, `GIT_EXEC_PATH`, `GIT_DIR`, `GIT_WORK_TREE`, `GIT_ALTERNATE_OBJECT_DIRECTORIES`, `GIT_OBJECT_DIRECTORY`, `GIT_NAMESPACE`, `GIT_ALLOW_PROTOCOL`, `GIT_TEMPLATE_DIR`, `XDG_CONFIG_HOME`, or an assignment of `HOME` or `PATH`) and also launches a shell, an interpreter, env, make, xargs, `find -exec` or git is refused wherever the variable sits, because it may be handed to a git that a nested program runs. This includes an ordinary `PATH=... make` and `GIT_DIR=... git status`; reading a variable (`echo $GIT_DIR`) or setting an unlisted one (`GIT_PAGER=cat git log`) is allowed.
- In the Brother source a piped patch is read by a fixed command the guard builds (`git diff --name-only --no-ext-diff --no-textconv` on revisions that resolve), never by re-running the agent's own `git diff` words; an option, a pathspec or an unresolvable word makes the patch unreadable and the command is refused. A path inside a `.git` folder is matched without regard to case, and a gitdir reached through a `.git` file's pointer is the same metadata. A `--pathspec-from-file` or `--stdin` list is read (from the file, redirect or here-document) and each line is joined with the `-C` prefix, C unquoted as git does (a line with malformed quoting counts as naming the marker), and judged. Every list is read both ways, split on NUL and split on lines (each line cut at its first NUL, as git cuts it), so a `-z` or `--pathspec-file-nul` in any spelling, bundled (`-zq`) or abbreviated (`--pathspec-file-n`), cannot change what is read, and an abbreviated `--pathspec-from-f` or `--std` is read like the full option; one that cannot be read counts as naming the marker. A piped patch is read only by comparing two commits, never the working tree, with attribute files and the system attributes switched off.
- HEAD moves other than reset, checkout, switch, rebase, filter-branch, filter-repo, replace, update-ref and symbolic-ref: for example `git revert` of the commit that added the marker file. In the Brother source those listed moves are refused when their target tree does not hold the marker; a stranger's repository is not affected.
- The spec contradiction (M6): a one liner's rmtree of a path outside the worktree is refused while `rm -rf` of the same path is allowed, because the frozen harness pins `/protected`. The owner decides which half of the spec stands.
- The unterminated-quote refusal is pinned by the frozen harness (`echo "unterminated` is refused), so it does not follow the rule above that allows an unsplittable command naming no tool.

## The commit gate on a machine that cannot judge private terms

When the only thing the commit scan finds in a lane is a private-terms hit, and the same scan also hits a text that names nothing (this machine has no private terms list, or no term scanner), that one count reads NO-DATA and the lane is still integrated; every other count still refuses it. This is a recorded owner decision (class 2): it is there so a machine without the list is not locked out, and it is undone by making `_run_scan` in `scripts/integrate.py` refuse commit_scan's exit status 3 and giving every test a scratch list instead.

## The one-process hook dispatcher is wired, and the host-live proof sees the dispatcher, not each handler

bundle/hooks/hooks.json registers one synchronous command per event, `python3 "${CLAUDE_PLUGIN_ROOT}/runtime/hooks/brother_hook.py" <Event>` (HD1.e), and that one process runs every handler of the event from the dispatch table in HOOKS-MANIFEST.json, so a Bash call no longer starts one interpreter per handler. Two things follow that are true and worth knowing. First, the HP1 host-live witness records each dispatcher fire, which is the call the host makes, with the merged answer the host reads; it does not record a row per handler, because the handlers no longer cross the host boundary, and a row a handler runner wrote about itself would be the hook vouching for itself rather than a witness outside it. Second, the real Claude Code 2.1.286 recording of 2026-10-04 was made on the per-handler shape (4 SessionStart hooks per session), so its tests now judge it against that run's own hook file (scripts/fixtures/hp1-real-2026-10-04/candidate/hooks/hooks.json), while the live crosscheck expects one fire per event; a fresh signed-in recording of the wired shape is the owner's to make with the steps in docs/how-to/host-live-proof.md. The rollback is BROTHER_HOOK_DISPATCH=spawn, which runs every handler as its own process through the same table; hook_guard.py is still shipped and still asked per handler.

## The loop token lane reports a holder's answer, not a provider's acceptance

The login refresh has two lanes. A seat lane runs a real login and reads the host's answer. The loop token lane asks the run's login holder for the saved token. The holder reads that token once and answers with its bytes. The refresh reads RENEWED on that answer. Nothing in that lane proves the provider accepted the token or renewed it. A seat whose login fails parks the run, and the park is explicit. A token that the provider rejects later fails at the call that used it, not at the refresh. Do not read a RENEWED from the token lane as an automatic renewal.
