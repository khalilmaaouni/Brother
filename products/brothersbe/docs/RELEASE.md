# Releases: how a version is cut, and how you pin one

This runbook exists because the laws change under their users. An install whose
only name is a commit hash cannot be talked about, compared, or pinned by a
human, and a security page that says "verify what you installed" without a
manifest to verify against is an invitation, not a control. This page is the
procedure; what it does NOT do is execute itself: every step below is run by a
human, and the two that publish are gated on one.

## The version scheme

Semantic versions in the `VERSION` file, one line, starting at `1.0.0-rc.1`.

- MAJOR: a law or a gate changes meaning, so a green run before and after does
  not attest the same thing.
- MINOR: a new check, law, or tool; existing verdicts keep their meaning.
- PATCH: fixes and copy that change no verdict.
- `-rc.N`: a candidate; the promises in `INVARIANTS.md` hold, the tag may still
  move before the final version. A version with no suffix is a cut release.

`DIGEST.md` names the version in its header, so an injected law block says
which version it came from; `tools/test_sbe.py` asserts the header matches
`VERSION` so the two cannot drift.

## Pinning an install to a release

See which tags are actually published before you pin to one; naming a
specific version here goes stale the moment the next one is cut, and, as of
this writing, would fail immediately (`docs/KNOWN-LIMITS.md`, "Only one tag
is published on origin"):

```bash
git ls-remote --tags <repository-url>
```

Then clone with the tag you saw:

```bash
git clone --branch <tag> --depth 1 <repository-url> ~/.claude/skills/brothersbe
```

Then verify the bytes you got against the manifest that release ships:

```bash
cd ~/.claude/skills/brothersbe && scripts/verify-install.sh
```

PASSED means your files match the manifest in both directions (nothing
missing, nothing altered, nothing extra). It does not prove the manifest is
authentic: take the manifest from the tag you trust, not from the same
untrusted channel as the code. If you do not pin to a tag, pin to a commit and
record the hash, as [SECURITY.md](../SECURITY.md) documents.

## Cutting a release (maintainer)

Before you start: free disk space above the 15 GiB floor that
`tools/sbe_stall_detector.py` enforces (`DISK_FLOOR`, default
`--disk-floor-gib 15`). The detector is the source of this figure; earlier
notes in this project named an 8 GiB pre-seal floor that disagreed with it,
corrected here to match so the two floors cannot drift apart again.

In this order, steps 1 to 5 in ONE commit, so no version of the tree ships a
manifest that disagrees with its own files:

1. Bump `VERSION` and the version named in the `DIGEST.md` header.
2. Write the `CHANGELOG.md` entry: newest first, each line naming the behavior
   that changed and the check or test that proves it.
3. Run every regeneration `sbe version bump` printed as a REMINDER, in the
   order it printed them. As of 2026-08-25 that is
   `evals/replay_book.py --write` (book echoes from live runs), `sbe book`
   (the booklet's generated sections, whose provenance is rendered FROM
   VERSION and goes stale the moment it moves), and
   `tools/regen_sandbox_guide.py` (sandbox guide head hashes, which a version
   bump always moves). Each writes TRACKED files. **The tool's printed list is
   the authority, not this line**: it is beside the code that moves the
   version, and this document is not. If the two ever disagree, the tool is
   right and this file is stale, which is a defect
   `TestTheReleaseDocNamesEveryStepTheToolPrints` now fails on.
4. Regenerate the manifest LAST, after `git add`:
   `scripts/checksums.sh CHECKSUMS.sha256`. Last is load bearing. Step 3
   writes tracked files, so a manifest generated before it ships stale, and
   this document used to say step 3 was the manifest with no step 3 at all
   above it. That ordering error is why this note exists.
5. Run the gates (`evals/run_evals.py`, `evals/test_no_data_class.py`,
   `tools/test_sbe.py`) and commit the files together only when green.
6. Tag: `git tag -a v<version> -m "<one line from the changelog>"`. Human-gated.
7. Push the tag. Human-gated, and on this machine it goes through the
   operator's own push process, never a bare push from a session.

## What has actually been executed

Honesty over ceremony. Steps 1 to 4 were executed for `1.0.0-rc.1` when that
version shipped, and have since been executed again for `1.0.0-rc.2`:
version set, `CHANGELOG.md` written, the manifest regenerated by the script
beside it (`scripts/checksums.sh`), and the gates green. The manifest is
regenerated in whatever commit last changed a tracked file, which an eval
forces on every wave, so it matches THIS TREE rather than the commit that
set VERSION; run `scripts/verify-install.sh` on a fresh clone to check that
for yourself instead of taking this sentence's word for it.

Steps 5 and 6 were executed for `1.0.0-rc.1` on 2026-07-31: annotated tag
cut and pushed to origin. That tag predates the guided skills and stays
behind `main`.

Step 5 was executed for `1.0.0-rc.2` on 2026-08-01: the annotated tag was
cut, locally, at the release commit. Step 6, publishing it, was NOT
executed. Verified on 2026-08-04 with `git ls-remote --tags origin` and
`gh api repos/khalilmaaouni/BrotherSBE/tags --jq '.[].name'`: both show only
`v1.0.0-rc.1` on origin. `v1.0.0-rc.2` exists as a local tag and nothing
more, until the product owner pushes it through their own push process.
This paragraph is updated when that changes, because a runbook that
presents untested steps as proven is the defect class this whole project
exists to catch.
